# AIBody – Specification (spec log)

Agreed status; this is what applies. Status (done/open): [`REQUIREMENTS.md`](REQUIREMENTS.md). Deferred ideas: [`BACKLOG.md`](BACKLOG.md).

## Goal
- Virt-A-Mate plugin (VaM 1.22) that gives an AI a body: speaking with lip sync, expressions, gestures, poses; listening through the microphone.
- Two parts: the plugin `AIBody` (C#) on the Person + the companion app `aibody_companion` (Python) next to VaM.
- **One companion app controls exactly one character** (Leon, 19.11.2026; see the entry "One character" below).

## Fixed constraints
- Sandbox: no `UnityWebRequest`, no `UnityEngine.Networking`, no `WWW`, no `System.IO`, no `Process`, no reflection (also no indexers `this[...]`: the compiler adds `System.Reflection.DefaultMemberAttribute`, which VaM's security check rejects), no `DllImport`, no Unity `Microphone`. `System.Net` and sockets only in the one file `SocketLink.cs` (see "Network"). The build scan fails otherwise (`tools/check_plugin.py`).
- Only evidenced VaM APIs (evidence in `docs/API_AUDIT.md`); anything without evidence is marked (`TODO(verify)`) or left out, not worked around.
- File access in the plugin only through `FileManagerSecure`.
- Internet access only in the companion app. The plugin may use one loopback socket to the companion app (Leon, 19.11.2026; see "Network").
- C# 6.
- One plugin, one `.cslist` (`Custom/Scripts/d0n/AIBody/AIBody.cslist`), exactly one MVRScript class; loaded in one step in the Person's Plugins tab.
- One `.var` (`d0n.AIBody.<N>.var`) into `<VaM>/AddonPackages/`.
- Version scheme from version 12: version = package number `<N>` of the `.var`; the same in the plugin display (`PluginVersion`), the companion app (`__version__`, pyproject), `packaging/AIBody.json` and the Git tag / release `v<N>`. Older tags (up to v0.7.4 = package 11) stay.
- Do not touch LICENSE and `licenseType` "FC" in `meta.json`; the license question is out of scope.
- No secrets in the repository; API keys never in the log (redacted).
- Everything is in English (Leon, 19.11.2026): code, comments, README, docs, plugin UI, release notes. Release notes give full paths from the VaM main folder, the loading location (Plugins tab of the Person) and ask for a screenshot, red `AIBody:` log lines and the console output of the companion app.
- Meaningful commits directly on `main`, each commit green on its own (tests, ruff, plugin check, schema check).

## Connection
- File transport through `<VaM>/Saves/PluginData/AIBody/default/` in both directions (commands in, events out), protocol v3 (`protocol/PROTOCOL.md`, schemas `protocol/schema/`). The folder name is fixed: one character, one folder.
- Optional loopback socket on top of the files (version 30, see "Network"); the files stay the fallback.
- Heartbeat on both sides; timeout 6 s → status "DISCONNECTED", automatic reconnect; old commands are discarded.
- The plugin stays stable without the companion app.

## Network
- Toggle **Network Active** (tab Config; `JSONStorableBool`, saved with the scene, mirrored as `connection.network_active` in config.json), **on by default** (Leon, 19.11.2026).
- Loopback only: `127.0.0.1`, one fixed address, port configurable (`connection.network_port`, default 38437, file only). No other address can be set in the plugin. Transport: UDP, chosen by source evidence (`docs/API_AUDIT.md`, "Version 30").
- The plugin never blocks the Unity main thread: background threads and queues, results are taken over in `Update`; no connect step; reconnect with a growing delay.
- Off = no network code is executed. The file exchange is the fallback and is used automatically whenever the socket cannot connect.
- Short status in the info field: `Network: off` / `connected` / `unavailable, using files`.
- The plugin shows no prompt of its own. VaM's global switch "Allow Plugins Network Access" and VaM's per-plugin prompt are outside AIBody's control; README and TECHNICAL say so.
- The companion app listens on `127.0.0.1` only, on by default, next to the file inbox, for one plugin. The token never travels over the socket (the app reads it from `config.json`).
- The plugin description carries one short hint about "Allow Plugins Network Access" (Leon, 19.11.2026): in the package description (`packaging/AIBody.json`, shown by VaM's package manager) and in the large info field of the plugin (`NETWORK: …` notice).

## Shared configuration
- One global file `<VaM>/Saves/PluginData/AIBody/config.json`, read by plugin and app; schema `protocol/schema/config.schema.json`, docs `docs/CONFIG.md`.
- Values in the plugin menu (saved with the scene) win and are written back; a scene without AIBody values takes over the file once.
- The section `ai` belongs to the companion app; the plugin only sets its menu values there (mode, voice, proactive talking, voice barge-in) and passes the key file paths on from the file (no menu field since version 15; the file wins on every start).

## API keys
- xAI needs an API key from console.x.ai; a Grok subscription / grok.com token does not work. Status displays and hints say so.
- Main input since version 21: free-text field **XAI API Token** (tab Voice, section Voice Mode, at API Reconnect). Plain text, no format check, no ElevenLabs field. Since version 24 (19.11.2026) the token is stored in `config.json` (`ai.xai.api_key`, plain text, Leon's explicit wish), filled into the field on start and then shown masked; it reaches the companion app in the `config` event (`keys.xai`) through the files and is never visible unredacted in the log.
- **Token masking (since version 30, Leon, 19.11.2026):** the first 4 and the last 4 characters stay visible with stars between them (`xai-****abcd`; the marker `****` stays). No masking while the field has focus (`InputField.isFocused`); the mask is applied when the focus is lost, not after a timer. `config.json` keeps the full token; since version 31 the field is not saved with the scene at all (the storable is not registered), so no scene holds the token or the mask.
- **First-run note (since version 30):** see the entry "First-run note" below.
- **Order for xAI (since version 24):** 1. the field (live, if not empty), 2. `ai.xai.api_key` in config.json, 3. environment variable `XAI_API_KEY`, 4. key file (`ai.xai.key_file`). An empty field falls back; emptying the field also empties `ai.xai.api_key`. ElevenLabs: `ELEVENLABS_API_KEY` (wins) or `ai.elevenlabs.key_file`, no field.
- A key entered in `key_file` is still rejected and not stored (applies only to these path fields in config.json, not to the token field).
- Key status per provider: configured / missing / rejected (with the reason).

## AI modes
- Default `qa` (simple Q&A): speech recognition xAI → Grok → voice xAI, speech only, no body control by the AI, no proactive speaking.
- Realtime optional (toggle "Use realtime voice" = `auto`): Grok Voice over `wss://api.x.ai/v1/realtime`, the chain as fallback.
- `chain`: exactly the engines chosen under Voice > AI Character.
- Test engines `null` / `echo` / `tone` for offline use and as the fallback without a key.
- Proactive speaking after a configurable silence (slider "Speech delay timer (s)" 0–3600, default 90; 0 = off, like the toggle "Proactive talking" off; info field "Proactive talking: on - after 90 s of silence the AI may speak on its own (speech delay timer, not the answer delay)" or "Proactive talking: off (speech delay timer 0 s)"); the AI is told the time and the time since the last exchange.

## Microphone
- Recording, VAD and echo gate only in the companion app; it always records from the system's default input device (sounddevice default). There is no microphone selection in the plugin.
- Push-to-talk is switched in the plugin and reported to the app; push-to-talk interrupts the running answer.
- No device menu, no "Refresh microphones" button, no microphone list and no `list_devices` / `devices` messages any more (19.11.2026). An old value `mic.device` in config.json, in a `config` event or in a scene ("Mic device") is silently ignored, no error.
- If the companion app is missing, the info field of the tab Client Character says in red: "Companion app not running, so nothing is heard or spoken. Start it in a console, in the 'companion' folder: python -m aibody_companion --vam-root "D:\VaM""; if *Active* is off, in red "The link to the companion app is switched off. Turn on 'Active' in tab Voice.". The status line "Mic:" shows capturing / not capturing, "microphone: system default input", the mode and the reason for an error.
- Anyone who wants another microphone sets it as the default input device in Windows. Diagnosis without VaM: `python -m aibody_companion --list-devices` or `python tools/mic_test.py` (output only, no selection).
- Test without VaM and the app: `tools/mic_test.py` (raw devices, per host API, the list as the app sends it; optionally into the plugin input).

## Voice output
- The answer is a local WAV file, played through VaM's audio loader on the head audio source with the built-in lip sync; no download by URL.
- Audio folder `Custom/Sounds/AIBody/default/`; if "not loadable", one switch to `Saves/PluginData/AIBody/default/audio/`.
- Speech does not depend on expressions; test tone directly and through the companion app.

## Body control
- Expressions through morphs, breathing, head idle; gestures through Timeline actions; poses through pose presets.
- The AI controls the body by tool call (realtime: `function_call`; chain: `/v1/responses` with tools): `express` (expression / gesture). Every tool call gets a result. Since version 32 there is **no `pose` tool** any more: poses are applied only through pose commands (below).
- No tools in `qa` and with Body control off.
- Poses: only through **pose commands** (version 32), plus a manual menu (select + apply, a user action) in the tab AI Character.

## Pose commands (since version 32, Leon, voice call 20.11.2026)
- **Vocabulary:** `config.json` > `poses.commands`, a list of `{"command": "<text>", "pose": "<pose id>"}` (AI Character level, one character). The starter set (Leon's wording, exact labels): `Sit Down`, `Lay Down`, `Prone`, `Stand Up`, `Spread Your Legs`, `Ankle Your Knees`, `Ankle Your Elbows`, `Turn Around`, `Crawl on all fours`, `Bend Over`; each is linked to a pose of the same name. A missing `poses.commands` key = the starter set; an empty list = no pose commands. At most 100 commands, 60 characters per command.
- **Hard gate (deterministic code in the companion, `aibody_companion/pose_commands.py`):** a pose may be emitted only when the user's ENTIRE input equals a known command after: trimming white space, lower-casing, removing trailing `.` `!` `?` `…` (and the full-width forms), and collapsing internal white space to one space. No substring and no fuzzy matching: `please sit down`, `sit down and smile`, `Sit-Down`, `sitdown` do NOT trigger. It applies to typed text, the microphone (speech-to-text result), the realtime transcript and the remote control's `pose` action. It is not left to the prompt: the language model is never asked, and it has no pose tool.
- **Reply (documented choice):** a matched command gets **no spoken reply and no language-model call**. The app sends the plugin the linked pose as JSON, `{"pose":"<id>"}` (`pose` command, field `json`, plus `command` for the log), and shows "Pose command: <command>" in the status line. Reasons: a spoken confirmation would need either fixed text in one language or the model (which could add words or ask follow-ups for what is a pure command), and silence keeps the gate fully deterministic. In realtime mode the server may already have started an answer when the transcript arrives: the app sends `response.cancel`, stops the speech, and drops a response that starts right after (8 s window). TODO(verify) with the real server (T26).
- **Validation on both sides:** the companion parses its own reply with the same strict reader as the plugin (`{"pose":"<non-empty text>"}`, exactly one key, no duplicate keys, nothing after the object, at most 400 characters); the plugin (`PoseVocabulary.ParsePoseJson`) parses again, looks the pose id up in ITS vocabulary (`FindByPoseId`), and resolves it to a real pose of the character. Unknown, malformed, or unlinked: ignored with a short English warning (`AIBody: Warning: Pose ignored: ...`), nothing is applied.
- **Unavailable commands:** a command whose pose does not exist (no `gestures.json` pose and no pose file with that name, matching ignores case, spaces, `_` and `-`) is kept in the config and listed as unavailable; it is never offered to the AI, never applied, and the app answers a typed or spoken match with a warning in the log and the status line only. Status field `pose_commands` carries `available` per command; the remote status lists `poses` (available) and `poses_unavailable`.
- **Plugin UI (tab AI Character > Poses):** the command chooser with **Delete Pose** (starter commands are deletable too), **Restore starter poses** (adds back the missing starters only; the user's own commands and changed links stay), **Add Pose** (type the command text in *New pose command*, choose the pose in the pose chooser above, press Add Pose; the same command text again only changes its link), **Apply pose** and **Reload poses** (manual apply is a user action in the menu, not a command). Every change is written to `config.json` > `poses.commands` (and read again at start and with *Reload Config JSON*). No empty menus (version 16).
- **Behaviour change:** before version 32 the AI could call a `pose` tool (all poses it was told about) and the remote `pose` action took a pose name; both bypassed any input rule. Now `pose` as a tool call is refused ("pose commands only"), the plugin refuses `kind: pose` entries as a gesture, and the `pose` command no longer accepts a `path` or `name`. Poses of `gestures.json` (`kind: pose`) and pose files only serve as the targets of pose commands.

AI Character: poses, hints, body status. Client Character: push-to-talk, microphone. Config: config.json, network, self-test, Recent events (Verbose log), Startup log. Only own texts are translated: field names, labels, headings, info and status texts and own fixed entries (e.g. "System default microphone"). Content that the operating system or VaM supplies in its language (microphone device names, names of the Windows default devices, host API names, system error messages) stays exactly as the system names it. ## Logging
- Verbose log (tab Config / `advanced.verbose_log` / `-v`): a trace per turn with turn number and time in the console and in `<VaM>/Saves/PluginData/AIBody/logs/companion.log` (1 MB × 5); in the plugin `[debug]` lines and *Recent events*.
- Self-test in the status field (since version 13): Person atom, head audio, morphs, pose memory (`PosePresets` with `presetBrowsePath`), number of poses and pose files, breath morph found, expression morphs x of y (missing names), Timeline storable for `timeline` gestures, PluginData writable, companion heartbeat.
- The body checks are recomputed at most every 5 s and sent as `selftest` in `ready` / `heartbeat`; the companion app writes it once per change as "Plugin self-test: ..." into the console and `companion.log` (a warning if something is missing). No new setting, no new VaM interface.

## Latency
- Measured from the end of the user's speech (VAD end, push-to-talk released, Enter; realtime: `speech_stopped`) to the first sound (`speech_started` of the plugin).
- Breakdown: STT, LLM first token, first sentence, TTS, file write, to plugin, plugin start (realtime: server first audio, segment, to plugin, plugin start).
- One log line per turn; last value and average of the last 10 in the status field (*Live*, "Latency to first sound").
